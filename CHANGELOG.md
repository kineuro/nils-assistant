# Changelog

All notable changes to the NILS assistant are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and versions follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html). The first release will be 1.0.0; until then pre-releases are tagged `v1.0.0-alpha.N`.

## [Unreleased]

### Added

- The find-data skill carries a card of exact shapes (2026-11-13, a live test). Asked for the subjects with two alike sessions, the chat guessed the grammar: its drafts were refused for an `attach` written as a name, a `pick` with a `limit`, a set written in place of its name and group keys the set did not have, three drafts went on probing which keys a part takes, and several searches on how to write the loose signature. The card shows `pick` (per, n, by, ties), `attach` (as, set, optional) with an attached row's field read as `<as>.<field>`, `has`, `same`, a group with its keys and its aggregates (`count`, `sum`, `distinct`, `min`), a group of a group, `bind` with `case`, the derived fields `acquisition_type`, `voxel` and `signature`, what a set does not take, and how a parent's field is named. Every line of it is a line of a worked example, each validated with the engine's `ask validate`; a test holds the card to those files. Two worked examples are new in the cookbook, the question asked in the live test answered with `pick`, `attach` and `same`, and the same sessions per subject and scanner through groups.
- `registry_search` says how a derived field is written, with the options the catalog lists (`["derived", {level: loose}, "signature"]`, where it answered "derived signature (stack)"), and finds the pack's comparability levels by name or by the words protocol, signature and comparable; the registry's summary lists the levels and the options of each derived field.

### Fixed

- A draft the registry could not read is told which part to write again. A document that does not parse is refused with one sentence and no path ("unknown field `limit`, expected one of `per`, `by`, `n`, `ties`", "invalid type: map, expected a string"), and `query_draft` answered it with "fix exactly the path and issue named". The next step is now read from the sentence: the part it names, by its name or by the keys it lists, with every key that part takes and one example the registry accepts; that a list or the name of a declared set was expected; the form of a clause; or that the YAML does not read at the line named.
- A question is called slow only when its own answer ran past the registry's limit (2026-11-13, a live test). `query_draft` read a draft whose diagnosis said its counts were cut (`diagnosis.unavailable`, code `timeout`) as a slow question, answered `slow: true` without asking for the count, and the chat proposed a job for a question that answers in three seconds: the funnel of a question with a `pick` is counted stage by stage inside the draft's own short time, which says nothing of how long the answer takes. Such a draft now goes on to the preview, asked with no time of its own and so with the door's whole limit, and the model gets the document, the count or the rows, and `stage_counts`, a plain note of which parts of the diagnosis are missing and that this is no slow question; the registry's pointer to the job path is left out of the diagnosis beside an answer that came. Only when that run itself times out (a 504, or a refusal with `code: "timeout"`) is the question `slow` and the job offered, as before with its document's number and never as a draft that did not validate. `query_run_readonly` does the same when only the diagnose door ran past its limit: the preview's answer is given with the note, where the whole call was told as slow.

- A job plan answered on either of its two cards is one outcome (2026-11-13, a live test). `propose_change` with kind `job_plan` keeps a change, whose card is decided at `POST /changes/{id}/decide`, and a plan, whose own card is confirmed at `POST /plans/{id}/confirm`; the desk shows both. A person confirmed the plan's card, and two things went wrong. The confirm door did not keep the person's token for the plan's conversation, as the decide door does, so the scheduler had no token to act with and the step that was due now stayed "waiting, the person's token is not held" until the desk's next token push: the door now keeps the bearer once the plan is the caller's, and a step due now is queued in the same call. And the change stayed open beside a plan that ran, so its card went on saying that it waited: confirming the plan now settles its change as approved, with a ledger row for the approval, and the door's answer carries the change (`change`). Approving the change still confirms the plan as now; approving it after the plan's own card was confirmed answers 200 with the same outcome and queues nothing twice, where it answered 409, and declining it then is refused with the reason. Declining an open job plan's change takes back its plan, still proposed, so no plan card is left to confirm. A change whose plan is no longer kept (plans are swept after the retention days) is `expired`, never open. The change's view gains `outcome`, one sentence of what happened (null while it waits), `GET /changes/{id}` reads a job plan's change with its plan, so one left open by an earlier version is settled when read, and each plan of `GET /inbox` carries `change` (the id, the state and the outcome of the change whose card proposed it, null for a plan no change proposed), so whoever draws the two cards can draw one.

## [1.0.0-alpha.33] - 2026-11-13

### Fixed

- A valid question that is too slow for the chat is told to the model as what it is, and gets a way to its answer (2026-11-13). The registry's timeout at the draft door was told as "the draft did not validate", with the instruction to fix the path and issue named, so the chat rewrote a valid question until the turn's work was spent; a preview that timed out was told as `preview: null`. A timeout is now its own outcome of `query_draft`, `query_run_readonly`, `query_read_rows` and `analysis_table`: `slow: true`, with the `document` id whenever the registry gave or held one, `valid: true`, `preview: {unavailable: "timeout"}`, and the next step, which is never another draft: a job plan for the document (`propose_change`, kind `job_plan`, steps `[{"verb": "run", "args": {"document": <id>}}]`). Read as a timeout: a 504, a refusal with `code: "timeout"`, and a draft answered 200 whose `diagnosis`, `funnel` or `preview` is marked unavailable by timeout. The same document sent again in the turn is answered without asking the registry; a draft the registry stopped before storing it says that nothing is stored; a fault of the registry (a 5xx) is no longer told as a draft that did not validate. The check before a turn settles sends back, once, a turn that left such a question without its plan or whose answer does not name the document.
- The assistant's own files default to the folder of the store. `ASSISTANT_LEDGER`, `ASSISTANT_NOTES`, `ASSISTANT_LINEAGE`, `ASSISTANT_LADDER`, `ASSISTANT_CHANGES`, `ASSISTANT_TEACHING` and `ASSISTANT_TEACHING_DIR` each defaulted to `./data` by itself, so an install that named its state folder for the others and not for the changes had its first proposal fail with "unable to open database file" in the middle of a chat. A file not named by its variable is now beside `ASSISTANT_STORE` (under `./data` as before when the store is unnamed or a Postgres URL; a file already kept under `./data` stays in use while there is none beside the store), its folder is made when missing, and every store is opened when the host starts: one that cannot be opened ends the start with one line naming its variable and its path. A variable set to nothing names no file.
- A job plan whose change cannot be kept leaves no plan behind. `propose_change` wrote the plan's rows first and the change after; when the change failed the model was told of an error, and the plan stayed as proposed, where the inbox listed it and `POST /plans/{id}/confirm` queued it. The plan is now taken back, a plan and its steps are kept in one transaction, and the model is told that nothing was proposed and nothing started. A tool that throws is told to the model as a fault of the assistant, never of the registry.
- `propose_change` with kind `job_plan` no longer makes the model guess. The schema lists the plan's verbs, the description carries the shape with one example, `steps` sent as JSON text is parsed instead of refused by the schema, a step's arguments written beside its verb are read, and a refusal for an unknown verb says how a stored question runs. The find-data and plan-work skills say when a question runs as a job.
- `registry_describe` answers `what: fields` (with `level`), as `registry_summary` does with `part: fields`; it was refused by the schema with no way on.
- A turn that ends at its guards is told which question it stored: a slow one by its number with the offer to run it as a job, else the last one drafted. It was told only to answer with what it had.

### Added

Parameters the person did not change are no longer sent, so the pack's rules set them. Nothing is set by the agent: a person approves the card, and an approved workflow runs at `POST /api/workflows/{id}/run`. The settle check holds the answer to every count the check gave. The bench gains the dev registry and fifteen questions with their bar (G13: 12 of 15 plans name the right analysis or workflow, and every skip reason is named), scored per run.
- Teaching (Wave 5 section 9.5) gains the two doors the desk's Teaching page needs. `GET /teaching/jobs` lists every fine-tune job, whoever started it, newest first, so an administrator can follow one until it ends (the inbox lists only a person's own). `POST /teaching/candidates/{id}/retire` retires a candidate through Kvasir's lifecycle; retiring the promoted one rolls the promotion back, so the backend's purposes go back to the model it is configured with, and the answer says so (`rolled_back`) with the promoted model per backend after it. The model the promotion replaced stays retired, as Kvasir never promotes a retired candidate again. Retiring needs `kvasir:work`, like the other lifecycle verbs; a candidate already retired is refused with a sentence.

### Fixed

- The steps of a dataset are read again when its summary says `counting: true`: the engine answers the kept counts at once while it reads them again, so the assistant waits a moment and reads up to three more times before it judges which steps have run, as the desk does.
- Every model call to Kvasir names its longest answer. The agent loop asked for none and Kvasir sent the model server none either, so a thinking model answered for as long as its context held: one call of 89,972 tokens over 65 minutes on the 27B (2026-10-16), and 190,783 tokens over 15 minutes on flash-next in a probe (2026-10-30). Where the caller names none, the call asks for the catalog's longest answer, kept inside what the context leaves; a caller's own is kept.
- `subject_resolve` no longer tells the chat that no subject has an ID when the value is a subject code. The T10 bench of 2026-10-16 asked it to erase subject SYN0005: 9 of 12 runs called the tool on the code and 7 of those, told that no subject has the ID, did not propose the erasure; 5 of 12 runs proposed it, against 12 of 12 before the tool existed. A value no ID type knows is now asked last as a subject code too, and the answer says when a value is one (the registry has that subject, or its subject was merged into another). A site with no map was never asked at all, because every type it keeps is flagged or the registry's own, and the tool answered that no subject had the ID without a call; and an engine that lists nothing to ask is no longer reported as an ID no subject has. The tool's description, the agent's rules and the find-data and check-identities skills say a subject code is no ID and needs no resolving, and the answer's next step serves work on the subject as well as a question about its scans. It needs the engine of the same wave, which answers a subject's own code at `POST /api/linkage/resolve` as the type `subject-code`; an older engine answers a code no row filed as unknown, as before.
- The bench's lexicon names `subject_resolve` and reads `POST linkage/resolve` as a lookup: the tool was counted a malformed call, and the lookup a write with no approval. A test holds the lexicon's tools to the agent's.

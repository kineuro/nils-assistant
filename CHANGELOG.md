# Changelog

All notable changes to the NILS assistant are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and versions follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html). The first release will be 1.0.0; until then pre-releases are tagged `v1.0.0-alpha.N`.

## [Unreleased]

### Added

- plan-analysis plans with the packs (record 57 P9, Wave 7b section 9). `registry_describe` with `what: pipelines` reads the engine's catalog instead of the table the skill carried: each analysis with its choices (the goal and the pack's switches), the settings a person may set, the settings its rules set per session, and the hard needs that skip a session, in the pack's own words; the families (one entry whose rules pick the method per session) and the workflows (`GET /api/workflows`) after them; `what: pipeline` gives one analysis, family or workflow in full, its needs, rules and checks each with its source. `propose_change` with `kind: analysis_plan` takes a `workflow` beside `pipeline`, a `dataset` (its main scans) beside a selection or cohorts, and the person's `goal`, `switches` and a workflow's `knobs`; it asks the engine first (the pre-flight, or `POST /api/workflows/{id}/plan` for a workflow) and the card and the answer name, in counts and the engine's words, the sessions left out (no main scan of a role), those that cannot run, those the pack skips (a hard need, or a fact the registry cannot tell), those a rule routes to another method, the caveats they run with, a workflow's links that are missing, redundant or refused, and what blocks a step. Parameters the person did not change are no longer sent, so the pack's rules set them. Nothing is set by the agent: a person approves the card, and an approved workflow runs at `POST /api/workflows/{id}/run`. The settle check holds the answer to every count the check gave. The bench gains the dev registry and fifteen questions with their bar (G13: 12 of 15 plans name the right analysis or workflow, and every skip reason is named), scored per run.
- Teaching (Wave 5 section 9.5) gains the two doors the desk's Teaching page needs. `GET /teaching/jobs` lists every fine-tune job, whoever started it, newest first, so an administrator can follow one until it ends (the inbox lists only a person's own). `POST /teaching/candidates/{id}/retire` retires a candidate through Kvasir's lifecycle; retiring the promoted one rolls the promotion back, so the backend's purposes go back to the model it is configured with, and the answer says so (`rolled_back`) with the promoted model per backend after it. The model the promotion replaced stays retired, as Kvasir never promotes a retired candidate again. Retiring needs `kvasir:work`, like the other lifecycle verbs; a candidate already retired is refused with a sentence.

### Fixed

- Every model call to Kvasir names its longest answer. The agent loop asked for none and Kvasir sent the model server none either, so a thinking model answered for as long as its context held: one call of 89,972 tokens over 65 minutes on the 27B (2026-10-16), and 190,783 tokens over 15 minutes on flash-next in a probe (2026-10-30). Where the caller names none, the call asks for the catalog's longest answer, kept inside what the context leaves; a caller's own is kept.
- `subject_resolve` no longer tells the chat that no subject has an ID when the value is a subject code. The T10 bench of 2026-10-16 asked it to erase subject SYN0005: 9 of 12 runs called the tool on the code and 7 of those, told that no subject has the ID, did not propose the erasure; 5 of 12 runs proposed it, against 12 of 12 before the tool existed. A value no ID type knows is now asked last as a subject code too, and the answer says when a value is one (the registry has that subject, or its subject was merged into another). A site with no map was never asked at all, because every type it keeps is flagged or the registry's own, and the tool answered that no subject had the ID without a call; and an engine that lists nothing to ask is no longer reported as an ID no subject has. The tool's description, the agent's rules and the find-data and check-identities skills say a subject code is no ID and needs no resolving, and the answer's next step serves work on the subject as well as a question about its scans. It needs the engine of the same wave, which answers a subject's own code at `POST /api/linkage/resolve` as the type `subject-code`; an older engine answers a code no row filed as unknown, as before.
- The bench's lexicon names `subject_resolve` and reads `POST linkage/resolve` as a lookup: the tool was counted a malformed call, and the lookup a write with no approval. A test holds the lexicon's tools to the agent's.

## [1.0.0-alpha.29] - 2026-10-16

Wave 7a's assistant after the beta, pinned by engine 1.0.0-alpha.82.

### Added

- `subject_resolve` (record 55, ruling 24): when a person names a subject by an ID (a study's own ID, a hospital ID), the one agent turns it into the subject code with the engine's `POST /api/linkage/resolve`, trying each ID type a person could name a subject by when they name none (one call per type, never a type flagged identifying unless the person names it (read from the same types list the names come from, a bare list or under `types`), moving past a type that is not there or a value that is not one of it; when every type refuses the person, it says their account may not look IDs up, never that the ID is unknown), and asks its question of that subject; an ID no subject has is said so, never answered for a whole cohort. The resolve goes through a seam of its own that acts for the person in the chat, the only one the redactor lets dial it, a station never, and spends none of ask-help's caps. The find-data and check-identities skills and the agent's rules say to resolve first. Tested on the question an admin asked of a ctrl-id, with a scripted model and a stub engine.
- Standing grants may be given for a whole page (`{page}`) or for everything (`{all: true}`), and are answered in words with their page: `GET /grants` carries `admin`, each grant's `page` and `words`, the ladder's rows with theirs, and `offer`, the actions the person may give grouped by page. A held step's reason names the action in words, never a door. A page's grant covers a door by the page the engine's policy row puts it on, as the offer reads it, and a grant given by its words covers every door the offer folds under those words.

### Changed

- An admin has full access to anything (record 55, ruling 24). A person holding `identity:work` is read as holding every grant at detail sensitive. Their planned steps need no standing grant: the scheduler reads the plan's person's own access from the engine with their token under no station's ceiling (one would strip the grant that makes an admin), only once a step's time and condition hold, kept a minute at most, dropped when the person's grants are seen to change and with the old readings of others cleared, and the seam made for the look is forgotten after it; a read that fails says so ("could not be read; trying again") and is tried again, never taken for a missing grant, and never keeps a stale reason. The one agent acting for them dials with the admin's own ceiling and content class, read fresh each turn and never from the conversation's saved mount, so a station's lower ceiling no longer turns an admin's answers into shapes, and an admin no longer, or a fork's reader, does not keep it. Everyone else keeps their grants, their detail and each station's ceiling.
- The grants vocabulary is suite version 3: `campaigns:see`, `campaigns:work`, `models:see` and `models:work` are no longer dropped from a person's grants, so campaign actions can be given as standing grants, and `sealed:see` is kept where a token names it. The test vectors are suite version 3's.
- The standing grants kept by door gain their page and words once (`grant_` gains `page` and `words`); the door stays the kept form.
- The tune-sorting-words skill writes its word change as typed rule operations (record 56, section 5.5): `add_words` and `remove_words` of the engine's patch contract, each with its scope, its reason and its evidence, rehearsed at the engine's rehearse door (`POST /api/packs/mri/rehearse`) over the whole registry, in place of an overlay tried at `POST /api/classify/try`. The scope is a dataset, a site, a maker, a batch, or `pack` for every site's sorting. The sorting's signals are read for every scope first (a dataset, a site or the whole pack under the pack's version), so a maker, a model or a station the registry does not hold, or a value no word reaches, is refused before anything is rehearsed. A rehearsal whose report does not say its cases held is not kept, and one that breaks an answer people gave is never proposed as it is: only when the person asks for it knowing that, with `accept_breaks` and the number of breaks in the sentence. A person's approval of the card proposes the change to the pack (`POST /api/packs/{name}/proposals`), where an operator adopts it on the Rules page; a card kept from before proposes its overlay there too, read by the engine as the word edits it is. No station's grant may hold the decision door, `packs/{name}/proposals/{id}/decide`.
- The bench, the evals and the tests name no real cohort (record 55, ruling 18): the seeded registry's third cohort is `cohort-d` (asked about as cohort D), the cohort the registry lacks is the Huntington cohort, and the memory guard's subject-code example is `STUDY-0012`. The briefs of analysis-plan and concierge, whose examples named a cohort, carry their new hashes, and the recorded runs under `bench/results` use the same names.

## [1.0.0-alpha.28] - 2026-10-14

### Added

- A saved selection named with @ in the chat (record 55 K6), as a kept result is: the desk writes `@[name](selection:name%402)`, every station's mention rule names the kind, and the one chat is told each turn what the mentions of the message name and which of its tools reads each, where that tool is mounted for the person. `query_read_rows` takes `selection` (name@version): the selections list door's row for its name (its versions, grain, description and note, a newer version named), the question of the version asked, and its size as the newest answer that froze it whole says it, a size held back at the person's detail said as held; with `page`, that answer's rows. An analysis over it is planned with `selection: name@version`, as before. The one agent reads `GET /api/ask/selections` and `GET /api/ask/selections/{name}` on its own seam, under the person's token.
- The analysis workspace (2026-10-12): for a person who may read the registry's rows, the one agent works in Flue's virtual sandbox, an in-memory filesystem with an emulated bash (just-bash 3.4.2), offline: no network, no host file, no process. `analysis_table` puts a stored question's rows (at most 2,000; a column the person sees only as shapes holds its shape text, marked as such) into it as CSV; the model computes with Flue's `bash`, `read` and `write` tools, each held to the turn's guards, over Python 3 with its standard library, xan, awk and jq, and draws with the workspace's `chart` command (bars, a histogram, boxes, lines, a scatter, as plain SVG). What it writes under `/out` reaches the person: a chart as a `chart` data part the desk shows as an image, a table as a `file` data part offered to download; the model never sees either part. Every limit says itself: 20 seconds and 1 MB printed per command, 512 MB for Python, 64 MB in the workspace, four charts of 200 kB and four files of 256 kB a turn. Six one-chat bench conversations cover it: a count and a mean by group, a refusal below the person's level, text planted in the registry, a chart and a file.
- One chat (record 55 B6): one agent, `nils` (`src/one/`), is the only voice of the chat. The stations' work became six skills it activates when a turn needs one (find-data, plan-work, plan-analysis, read-run, tune-sorting-words, check-identities), and about ten tools are mounted from the person's grants for the conversation's life. Each turn starts with the facts: what the registry holds, its datasets and their steps, what the person may do, and a hint from the words. The guards are code: a turn cap, a token cap, the repeat detector, one read-only sub-agent at a time, and the active skill's checks and plain words before a turn settles. Its model calls carry the concierge's Kvasir purpose. It writes nothing itself: `propose_change` puts a card before the person.
- The changes doors, `GET /changes/{id}` and `POST /changes/{id}/decide` (approved or declined). A decision is recorded first, and an approval is applied by the host under the person's token: a job plan is confirmed, an analysis queued, sorting words proposed as an overlay, a merge made at the engine's merge door, and an identity rule recorded.
- Settings: `ASSISTANT_ONE_CHAT` (`0` serves no one agent), `ASSISTANT_CHANGES` (the changes' store, `./data/changes.sqlite` unless said) and `ONE_CHAT_FIND` (`subagent` gives finding data to a read-only sub-agent instead of a skill).
- The one-chat bench: `npm run bench:one-chat` drives forty-two multi-turn conversations, each three times, graded on outcomes with pass@1 and pass^3 (`bench/ONE-CHAT.md`), and `npm run bench:one-chat-stub` serves a stand-in that speaks its interface where no model runs. The stations' live runs on the local 27B of 2026-10-08 and 2026-10-09 are in `bench/results/`.
- identity-check proposes a merge (record 55 K9): a dataset's probe names the subjects whose birth date and sex agree and whose visits overlap, by their codes, and `propose_merge` takes one such pair, the subject kept first, with why. The result carries `merge` (`subjects`, `canonical`, `alias`, `agree`, `visits`, `why`, and `act`, the body a person sends to the engine's merge door, `POST /api/linkage/merge`); the station never merges and never dials that door. The check `merge_named` asks for the merge when the probe named a pair and refuses one it did not, and the merge's two codes are the one exception to shapes only.
- `npm run bench:offline`: a station's question set run through its own code against a seeded engine with a stub model, no model and no network.

### Changed

- A list the engine holds back whole at detail plain reaches the model as held back, never as an empty answer (record 55 K7, small lists, the ruling of 2026-10-13: an answer that lists 1 to 4 subjects a quasi-identifying field chose has no row, `row_count` null and every column in `held_back`; its handle holds no rows, its rows door answers 404, and a set, a start or a cohort made from it is refused with 409). Every reader writes its rows, and its row count, as `held back (a list of fewer than 5 subjects; its length is a count, so no row is shown)` with one line, `held_list`, in place of the `held_back` line: the stations' compact preview and doors, and the one chat's query_draft, query_run_readonly, query_read_rows (a handle with no page answers from the handle), jobs_read and analysis_table. The engine's 409 on such a handle is said as held, never as a failure, and a run planned over such a list says why it cannot be checked. The check before a turn settles sends back an answer that calls such a list empty, none or nothing, or gives it a size, and the one agent's rules say to give it as held back to protect a small group.
- A count the engine holds back at detail plain reaches the model as held, never as none (record 55 K7, small counts, the ruling of 2026-10-12: a count of fewer than 5 subjects a quasi-identifying field chose or grouped is null, and one more beside it so that it is not found by subtraction). Every reader writes such a null as `held back (fewer than 5, or hidden beside a small count so it cannot be worked out)`, the same words for every held count, since one held beside a small one is not under 5 itself and two labels would say which is the small one, and says once what it means: a diagnosis's stages, drops, clause groups, ties and coarse rows (`held_counts`, first so no shortening drops it), a count preview's rows and a page of a result where `held_back` names the column with a count's why, a job's result, and the rows of a set the desk's page sends (`funnel` admits null). The `held_back` line and the one agent's rules say the chat gives such a number as held back to protect a small group, never "fewer than 5" as a fact about that count, never 0, none or a number, and never works it out from a total or the counts around it. A held mean or spread stays null, as before. A station's `funnel` part admits null counts.
- An answer's columns that came back as shapes (record 55 K7, with the engine of 2026-10-12): wherever the assistant hands an answer's rows to a model (a question's preview, its run and the pages after it, a result and its rows, a question run as a job, `analysis_table`, and the stations' draft, preview, result and rows), the columns the engine names in `shaped` reach the model as one plain line: "These columns came back as shapes at your detail: ...; their values are not known to you." The analysis workspace writes such a column to the CSV as its shape text and marks it `(shapes only)` in the column list; its next steps keep it out of Python and `chart`, and `chart` refuses to draw it. Shapes are told by their look only where an engine names none. The one agent's rules, and a check before a turn settles, hold its answer to stating and guessing no value of such a column and to saying plainly that the person's detail does not show it and that an admin can give that access. The find-data skill shows the aggregate form the engine reads, `["min", {set: <set>}, ["field", {}, "age"]]`, with the column after the options and never as an option.
- Flue 2.2.2 and pi-ai 0.87.1, from 2.0.5 and 0.83.0. Since pi 0.86 a provider gets the prompt and the tools as system messages in the transcript; the Kvasir provider and the title call send the transcript collapsed, as pi does for a model that takes a system message only first, because Kvasir's own pi reads only the prompt and the tools.
- identity-check probes a dataset by its name (`{dataset}`), which the engine's probe door now takes, instead of `root: @<name>/originals`, which it refused.
- identity-check reads a held shape as a second kind of identifier also when the rule read it only on the files held under it, beside the rule's own shape on files that are not held (a study number in a few files' PatientID).
- `nils_dataset` without a name answers the datasets by name.

### Fixed

- The one agent's caps hold its model calls too. Once the tools are stopped, or the turn's model calls, tokens or time are spent, the model gets one call to answer and the call after it is refused. A model that kept calling the framework's own tools after a stop was called again until the submission's hour ran out.
- `POST /changes/{id}/decide` checks that the change is the caller's before it keeps their token for the change's conversation. A stranger's decision learns nothing of the change, a question version's kind included.
- After the runtime summarizes a conversation's earlier turns, the next turn tells the facts again, whole.
- An analysis card names whom the run covers and its settings, read from the command its approval queues.
- `/capabilities` lists the one agent under the purpose its calls carry, `assistant.concierge`, and names the runtime versions in use.
- An answer a check sends back is marked replaced: the turn writes the data part `replaced` (`{kind: "replaced"}`) right after the step whose words it sent back, so the desk shows the answer written after the check alone, live and when the conversation is opened again. A desk showed both answers one after the other.
- The analyse-table skill is read as well as mounted. A person who may query the registry had it among the conversation's skills and the hint named it, but its text was never loaded, so activating it gave the model a miss; the agent now reads every skill the mount lists, in its order. The hint for a file asked for no longer says that a chart or a file of something worked out cannot be made yet: it names the workspace and that skill.
- Reasoning a model wrote as a `<thinking>` tag is read apart from its answer, beside `<think>` and the other families' markers, in a run's reply and in a shared conversation. The splitter (`src/host/reasoning.ts`) is now the module shared with Kvasir, its home: it is changed only there and copied here unchanged, and a test checks its stamp, so a copy edited in place fails.

## [1.0.0-alpha.27] - 2026-09-25

### Added

## [1.0.0-alpha.25] - 2026-09-16

### Added

- identity-check runs over a dataset: the run names a dataset, reads what it declares (its current identity rule, what arrives, what it holds), the identifier types the registry knows and the identifiers the dataset holds as shapes, and probes the current rule and a candidate over the dataset's originals as the root `@name/originals`. The proposed rule names a known type or proposes a new one with a description, and the verdict reads the held shapes against the rule's: alike, they are unmapped identifiers of the rule's kind and a map is needed, not a rule change; unlike, a second kind of identifier is on the dataset. Two checks say so, `type_named` and `held_read`; the result gains `dataset`, `new_type`, `held` and `map_needed`. The station still never sees a value and never reads a file. A station may now dial the two linkage reads that answer names and shapes only; every other linkage door stays refused, and the map, the reveal, coding the held and the merge are named among the forbidden doors.
- keyword-tune tunes any word list: a bucket the pack names, or the word list of one axis value, named `axis.value`. The hypothesis takes `bucket` or `value`, the overlay names a value's list under `lists` and a bucket under `buckets`, the survey reads the signals by value where the engine reports them, and the pack's own lists are read with `nils_pack` so a term the list already holds is never added. The `one_file` check counts one list of either kind; the result gains `list` and `value`.
- The operator plans `bring_in {dataset}`, the chain the engine queues (pseudonymise, then digest, fingerprint and classify), and `pseudonymize {dataset, name?, held?}`, both rung two under a standing grant for the job door and both data work. A step naming a dataset the person may not work on is refused at planning with the words the standing-grant door uses. The scheduler fires a `bring_in` when the batch lands like a digest, and follows the chain a job reports so the step after it waits for the whole chain.
